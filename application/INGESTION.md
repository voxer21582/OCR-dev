# Ingestion Baseline (pre-OCR)

## Current contract
`inventory_stream(stream, filename)` accepts non-seekable binary upload bodies directly, snapshots them in bounded memory, sanitizes the display basename, and applies the same inventory checks without writing the uploaded source to disk. `inventory_upload(path)` is a path convenience wrapper over that API. `inventory_upload` accepts regular PDF, PNG, JPEG, TIFF, or WebP files and ZIP bundles containing those formats. It identifies content by magic bytes (including RIFF/WEBP at bytes 0 and 8), hashes original bytes, validates ZIP member names and file types, rejects duplicate paths, symlinks, encrypted members, nested ZIP files, unsupported types, extension/content mismatches, and reads archive members under bounded limits. It never extracts archive paths to disk. Hashing and format validation operate on the same bounded in-memory byte snapshot, preventing a path replacement between source hashing and archive inspection from binding the hash to different contents. Exact SHA-256 duplicates are reported within ZIPs and across batches without deleting, merging, or auto-rejecting any occurrence. A successful inventory currently reports the legacy status `pending_security_scan`; that label does not represent a scanner wired into the local browser app. The user selected no antivirus integration, so scanning is not a product gate. The separate `scan_stream_upload`/`scan_upload` functions remain an unused optional adapter contract and no scanner is selected. Intake status alone is not a malware or decode-safety verdict.

## Provisional limits

| Limit | Default | Rationale / status |
|---|---:|---|
| Upload size | 25 MiB | Conservative prototype ceiling; revise with private operational requirements |
| ZIP members, including directory entries | 100 | Bounds document fan-out and central-directory allocation; preflight rejects excess entries before `ZipFile` builds its member index |
| One expanded member | 25 MiB | Matches single-upload ceiling |
| Total expanded ZIP size | 100 MiB | Bounds aggregate decompression |
| Compression ratio | 100:1 | Rejects extreme expansion |
| Image header inspection | 1 MiB | Bounds metadata scanning before pixel decoding |
| Raster dimension | 12,000 px per side | Provisional; adjust with private workload |
| Raster pixel count | 50,000,000 per page | Reject oversized canvases before decoding |
| TIFF pages | 100 | Provisional page-count ceiling |
| Nested ZIP | Rejected | Avoids recursive archive processing |

For Classic TIFF inventory, the 1 MiB header setting is a cumulative per-document metadata-read budget: linked image directories may be located beyond the first MiB of an already bounded snapshot. Every metadata read, including overlaps, consumes budget. TIFF IFDs with duplicate width or height tags are rejected as ambiguous; this is stricter than the earlier prefix parser. BigTIFF is not supported. This inspection checks dimensions and page limits, not complete TIFF conformance or decoder safety. The byte-prefix inspection API retains prefix semantics.

ZIP inventory now buffers one bounded member at a time for hashing, classification and metadata inspection, including members that are not TIFF. With default limits, inventory can hold an upload payload up to 25 MiB plus one expanded member payload up to 25 MiB, a 64 KiB chunk and up to 1 MiB of non-TIFF raster header data; Python allocation capacity and temporary copies add variable overhead. These are payload bounds, not a precise resident-memory ceiling, and do not describe materialization or batch APIs. Member streams are consumed through EOF for CRC and checked against declared and actual size budgets.

The repository-root required check explicitly runs selected application tests, including `test_ingestion`; the new TIFF-specific test module requires a separately reviewed CI selector.

## Verification
The synthetic suite covers PDF signature/hash inventory; PNG/JPEG/WebP dimensions; TIFF dimensions and page counts; pixel/page limits; animated-image rejection; WebP top-level and ZIP signature inventory, ZIP document inventory without extraction, exact-content duplicate reporting without data loss, traversal and Windows absolute paths, duplicate member paths, symlinks, extension mismatch, unsupported members, malformed ZIP, entry-count, per-file/aggregate size, compression-ratio limits, and fail-closed scanner outcomes. It uses generated bytes only and never reads real company documents.
# Optional scanner adapter (not part of the local product flow)

`security_gate.py` is an unused fail-closed adapter experiment. The user selected no antivirus integration, so the local browser product does not invoke this module and its outcomes are not an OCR gate. The inventory's `pending_security_scan` string is a legacy placeholder, not a scanner verdict. No antivirus product or cloud scanning service is bundled or selected.

The scanner receives only media kind and a non-seekable stream, not the original filename or archive path. It must return scanner identity/version and the SHA-256/byte count it scanned. The gate independently hashes bytes consumed by the adapter and compares both reports to the initial inventory. Synthetic tests use an in-memory fake scanner; they prove state transitions and byte-binding, not malware-detection efficacy.

The adapter tests prove byte-binding for a hypothetical scanner only; they do not prove malware detection. Scanner selection is out of the selected scope.


## Optional cross-batch fingerprint registry
`fingerprints.py` provides an opt-in SQLite registry for exact-content duplicate detection across separate runs. The caller must supply the database path; there is no implicit project-data directory. It stores only a role (`document`/`archive`), SHA-256, and occurrence count. It never stores source filename, employee identity, or file bytes, and reports repeated occurrences without deleting, merging, or rejecting them. Exact-byte matching will not detect rescans, recompression, crops, or altered metadata.

A SHA-256 fingerprint is still linkable metadata. Treat the database as sensitive: place it only in an approved private location, restrict access, define retention/deletion and backup behavior, and protect it at rest using the host's approved storage controls. This prototype does not encrypt the database or apply a retention policy. The SQLite tests use temporary synthetic-only databases.
