# Document and Evidence Schema (initial contract)

Schema status: design baseline, version `0.1.0`; no production compatibility promise. Canonical serialization is UTF-8 JSON. Amounts use decimal strings, not binary floating point.

## Document record
- `schema_version`: version string.
- `document_id`: opaque identifier; must not encode employee identity.
- `source`: `sha256`, media type, byte length, original filename (sensitive local metadata), received timestamp, an opaque `storage_ref` that in the selected mode points only to the active in-memory session, and page count when known. It is not a durable storage location; clear/idle expiry removes the associated bytes.
- `document_family`: `invoice | fiscal_receipt | parking_receipt | hotel_document | unknown`.
- `language`: `it | en | mixed | unknown`.
- `pages`: ordered page inventory and dimensions/orientation.
- `processing`: stage status/version/configuration references; OCR, semantic extraction, document validation, and administrative verification have independent status.
- `fields`: named field candidates.
- `validation_findings`: rule identifier, severity, evidence references, and outcome.
- `review`: queue state and ordered event history. The Python ledger verifies event hashes, sequence, timestamp ordering, state transitions, actor reference, source-bound field candidates, evidence-bound document-family selections from OCR alternatives, and evidence-bound fiscal-state corrections with reason codes. The local browser provides a separate evidence-backed fiscal-state review control; a reviewed `pos_slip` cannot be assigned `fiscal_document` status. It returns a new record and never rewrites extracted fields or the top-level extracted fiscal state. `reviewed_overlay()` verifies the ledger and returns complete extracted and reviewed views side by side; the latest corrections overlay the reviewed view, while untouched fields and the original document family and fiscal state remain available as source values. A reviewed document family is kept separate from fiscal-document classification. In the selected local single-user mode, the ledger is an append-only, hash-chained review record within the volatile session; its opaque `actor_id` is local attribution, not authentication or identity management. Stronger external anchoring/authenticated identities would be a separate future deployment decision.

## Field candidate
Each candidate contains `value` (typed scalar/object or null), `status` (`observed | uncertain | unreadable | absent | not_applicable | rejected`), `alternatives` (zero or more value/status pairs), `confidence` (optional numeric 0..1, explicitly scoped to this field and engine), `evidence[]`, and `normalization` (rule/version and original literal when normalized).

## Evidence reference
`source_sha256`, `page_number` (1-based), `region` (normalized polygon [0,1] coordinates in page space where available), `text_span` or OCR token IDs, `literal` (sensitive; access-controlled), `producer` (OCR/model/version), and optional crop reference. Evidence must point to original bytes; generated text alone is not source evidence.

## Distinct semantic groups
- Expense note context: for an explicitly selected `expense_report` only, `traveler_name`, `trip_destination`, and `trip_purpose` are proposed only from explicit Italian/English labels in the same OCR token. `trip_start_date` and `trip_end_date` likewise require explicit “inizio/fine trasferta” or “trip start/end” labels. All remain uncertain and retain the entire labeled token as evidence; free text and other document families are ignored.
- Identity/roles: merchant/supplier, buyer references, tax identifiers, and payment recipient are distinct concepts. The semantic proposal layer currently recognizes only explicit `Bill to` and `Sold to` labels as separate uncertain `bill_to_name` and `sold_to_name` candidates. Generic `Cliente`/`Customer`, `Destinatario`, and payment-recipient cues are not mapped to either buyer field because their legal/payment roles can differ.
- Dates: generic `date_candidates` remain distinct from role-specific issue, check-in, and check-out candidates. Role-specific proposals require an explicit same-token Italian or English label and remain uncertain, with label and date evidence preserved. Service/stay and payment dates remain separate fields.
- Financial: subtotal, taxable base, VAT rate/amount, total, tip, currency, payment amount, with document meaning preserved. Generic numeric values remain `amount_candidates`; `total_amount` receives a separate review-required proposal only when the same OCR token contains an explicit Italian or English total label.
- Tips: `tip_amount` is separate from `payment_amount` and `total_amount`; it requires an explicit Italian or English tip/gratuity label at the start of the same OCR token and remains uncertain. Unlabeled amounts and amounts due do not become tips.
- Payment evidence: `payment_reference` is separate from authorization codes and invoice numbers; it requires an explicit transaction/payment-reference label. `payment_method` and `payment_amount` are separate uncertain candidates and require explicit cues at the start of the same OCR token. The canonical name `payment_amount` means an explicitly labeled paid amount; it is not an alias for `total_amount` or an amount due. Method values are limited to an explicit controlled vocabulary (cash, card, bank transfer, cheque). Generic payment wording, POS logos, authorization/reference codes, and payee names do not establish payment method or paid amount. POS evidence does not establish fiscal-document status.
- Relations: line items and totals with evidence; optional links to expense claims/movements are later-stage proposals, never approvals.

## Invariants
No field marked confirmed without evidence; no silent normalization or currency conversion; no invented values; alternatives survive uncertainty; source hashes bind evidence; validation findings do not overwrite OCR observations; administrative decisions are separate and human-attributed. `fiscal_document_state` evidence for fiscal, payment-evidence, not-fiscal, and uncertain classifications must bind to the source hash and inventoried page; unknown may have no evidence. A POS slip cannot establish fiscal-document status. The machine-readable Draft 2020-12 contract is stored at `src/alfa_document_intelligence/schemas/document.schema.json` with ID `urn:alfa:document-intelligence:document-schema:0.1.0`. The Python cross-record checker in `contracts.py` verifies field and classification evidence source-hash/page binding, candidate/alternative status and value consistency, decimal-string values, and the POS/fiscal separation. `semantic_proposals.py` emits review-required generic dates, explicitly labeled issue/check-in/check-out dates, generic amounts, explicitly labeled totals, and explicit currency candidates. It also proposes taxable base, VAT amount, and VAT rate only from explicit Italian/English labels and same-token evidence, plus merchant/supplier names only from explicit role labels on the same OCR token. `tip_amount` requires an explicit tip/gratuity label (`Mancia`, `Importo di mancia`, `Tip`, or `Gratuity`) before the amount in the same token. `payment_reference` requires an explicit transaction/payment-reference label and preserves its identifier as an uncertain proposal; generic references, authorization codes, and invoice numbers are excluded. `payment_amount` requires an explicit paid-amount label (`Importo pagato`, `Somma pagata`, `Pagato`, `Amount paid`, or `Paid amount`) before the amount in the same token. `payment_method` requires an explicit method cue and a controlled same-token value. These candidates remain uncertain; generic due/payment wording, POS labels, authorization codes, and payee names are not mapped. Tax-role candidates remain uncertain; no VAT is calculated or inferred from totals or rates. The schema parses as JSON; formal JSON Schema meta-validation and instance validation remain pending selection of an approved validator dependency.

## Document validation findings
The `trip-date-order` rule applies only to expense reports when both trip start and end candidates are present. Observed canonical ISO dates pass when start is no later than end and fail when reversed; other statuses or invalid dates produce an indeterminate warning. A missing candidate produces no finding. Evidence is retained and the finding is not an administrative decision.
Findings have a stable rule identifier and version, validation dimension, severity, outcome (`pass | fail | indeterminate`), field names, message code, and source-bound evidence references. A finding reports a deterministic relationship only; it does not overwrite field candidates, establish legal/fiscal validity, or authorize administrative action. The `hotel-stay-date-order` rule compares check-in and check-out only when both fields have observed ISO dates; uncertain or unreadable values produce an indeterminate finding. The `taxable-base-vat-total-arithmetic` rule runs only for invoice, fiscal receipt, and hotel document records when taxable base, VAT amount, and total candidates are all present. It reports an informational pass only for exact decimal-string addition of three observed values. Any mismatch, uncertain status, or non-canonical amount produces an indeterminate review warning; missing components produce no finding. It never labels the record fiscally invalid, assumes a VAT rate, calculates tax, or accounts for discounts/other charges.

## Manual ChatGPT note-drafting handoff (implemented; no persistent draft schema)

The selected flow is user-initiated and manual. The local app prepares a copyable prompt from human-confirmed fields in an explicit allowlist: traveler/trip context and note totals/currency for the expense note; merchant, date, totals/currency, tax amounts/rate, paid amount, and tip for supporting documents. Tax identifiers, payment references/methods, document numbers, and unrelated confirmed fields are excluded. Evidence page references are included. It excludes original files, raw OCR, filenames, source hashes, and unreviewed candidates. The user decides whether to paste the text into ChatGPT and must follow applicable company authorization. The app makes no ChatGPT API/network call.

The user can manually return generated text to the same volatile session. It is HTML-escaped and labeled as an unapproved draft; it does not modify extracted or reviewed fields and is removed on clear or idle expiry. The text is untrusted and must be checked against original documents. The prompt asks ChatGPT not to invent facts, but the application does not validate every returned statement or certify unsupported details. There is no durable `note_draft` object or provider/model record in the document schema because the current manual flow is session state, not an application model integration. No generated text can approve a reimbursement, payment, or accounting entry.
